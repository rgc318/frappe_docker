# AI 自然语言查询与业务检索改进方案

更新时间：2026-07-26

本文是当前项目关于“自然语言理解、业务工具调用、关键词检索和语义检索”边界的设计事实源。它解决的核心问题是：用户说“查询迪莫”时，系统应能把“迪莫”作为受控查询参数；用户说“商品迪莫”“迪莫商品”或“适合拍照的相机”时，也应在不牺牲权限和事实准确性的前提下稳定找到候选。

## 一、先澄清当前实现

当前商品只读查询并不是完整的模型自主 Tool Calling。实际流程是：

```text
用户消息
  ↓
Frappe 本地场景判断
  ↓
Frappe 提取商品查询词
  ↓
search_product_v2(search_key=...)
  ↓
可选 search_products_semantic(...)
  ↓
权限、启用状态、业务上下文和实时库存/价格复核
  ↓
AI Orchestrator 只根据受控结果组织回答
```

因此：

- 明确的商品编码、条码、名称查询不需要向量索引；普通数据库查询即可完成。
- 向量索引只用于同义表达、词序变化、昵称、规格、用途和描述性表达的候选召回。
- 当前 `tool_calls` 主要是后端真实工具执行后的审计事件，不等于模型先决定函数名和参数再调用数据库。
- 订单和报表优先调用 `erp-intent-v3` 严格 Schema 解析，Frappe 仍保留本地 DSL 作为快速路径和失败回退；结构化结果只用于选择白名单查询参数。
- 销售、采购和库存草稿是“Orchestrator 结构化候选 + Frappe 事实解析与校验”，这条边界是正确的，但商品、客户、供应商和仓库的实体解析尚未完全统一。

## 二、目标架构

采用业界常见的“模型理解、后端执行、事实回填”模式，但不让模型直接访问 ERP 数据库：

```text
自然语言
  ↓
AI 结构化意图/实体解析
  intent: product_search | order_query | report_summary | draft
  entities: item/customer/supplier/warehouse
  filters: date/status/amount/sort/limit
  ↓
Frappe 受控解析器
  1. 精确编码、条码、名称、昵称
  2. 中文归一化与别名
  3. 关键词/列表接口
  4. 未找到或有歧义时使用语义向量候选
  ↓
权限、公司、启用状态、业务上下文过滤
  ↓
实时 ERP 查询
  ↓
AI 仅组织真实结果，不创造事实
```

核心原则：

1. 精确查询优先，不让向量服务成为所有查询的前置依赖。
2. 语义检索是召回增强层，不是事实源；事实必须来自 ERP 正式服务。
3. 模型可以提出工具和参数，但后端必须使用白名单、Schema、权限和业务服务重新校验。
4. 多轮会话使用短期消息历史加受控 `conversation-state-v1` 工作状态；状态只帮助解析“它/刚才那个/只看未完成”等省略表达，不是 ERP 事实缓存。
5. 无法唯一匹配时返回候选并要求用户确认，不能因为“只有一个模糊候选”就自动写入单据。
6. 语义服务关闭、索引为空或 Provider 不可用时，系统应明确记录 `lexical_fallback`，而不是假装完成了语义理解。

## 三、分阶段改进

### P0：统一商品实体解析

新增共享的商品解析边界，供商品查询、销售草稿、采购草稿和库存草稿共同使用：

```text
resolve_item_candidates(query, company, context, warehouse, limit)
```

返回至少包含：

```json
{
  "status": "resolved | ambiguous | not_found",
  "selected": {},
  "candidates": [],
  "match_method": "exact | normalized | lexical | semantic | hybrid",
  "confidence": 0.0,
  "semantic_available": true
}
```

解析顺序：

1. 条码、Item Code、精确名称。
2. Unicode NFKC、大小写、空白、全角符号归一化。
3. 去除通用请求外壳，例如“查询一下”“商品：”，但保留原始 query 给语义检索。
4. 复用 `search_product_v2` 做后端关键词候选。
5. 只有无结果、结果过多或查询明显是描述性表达时，才使用 `search_products_semantic`。
6. 最终重新执行 Item 权限、启用状态、销售/采购/库存上下文和公司过滤。

不要继续在单个函数中无限增加“以某词开头/以某词结尾”的正则分支。规则只负责通用归一化，实体匹配由统一解析器完成。

### P1：开启语义能力，但先治理索引

向量能力不能只改开关。正式启用前必须：

- 对全部有效 Item 执行完整重建，而不是只索引一个测试商品。
- 清理历史测试商品、失效 Item 和已删除对象的向量点。
- 校验 Qdrant point 数、Embedding 维度、alias、索引版本和 Provider 模型一致。
- 使用中文同义/词序/描述性评测集验证 Top-1、Top-3、误召回、权限泄露和删除恢复。
- 通过质量门禁后再把 staging 的 `MYAPP_AI_VECTOR_SEARCH_ENABLED` 持久设为 `1`。

索引不完整时，即使 Embedding 服务正常，也可能出现漏召回或测试商品噪声；这属于数据治理问题，不是模型“不会理解”。

### P2：统一客户、供应商和仓库解析

客户、供应商、仓库先复用精确/归一化/关键词候选，并统一返回 `resolved / ambiguous / not_found`。只有数据量、别名和自然语言需求证明必要时，再为这些主数据增加独立语义索引。

商品向量索引不能直接代替客户、供应商和仓库解析，也不能把所有主数据无差别塞进同一个 collection。

### P3：继续扩展结构化订单与报表意图解析

订单和报表当前已经接入严格 JSON Schema 的查询意图解析，DSL 作为安全兜底；后续重点是扩大实体、口径和歧义评测，而不是删除后端校验。当前 Schema 示例：

```json
{
  "intent": "order_query",
  "entities": ["sales_order", "sales_invoice"],
  "company": null,
  "date_range": { "from": null, "to": null, "preset": "latest" },
  "status": "unfinished",
  "sort": "amount_desc",
  "limit": 5,
  "min_amount": null
}
```

Frappe 只接受 Schema 允许的枚举和字段，再转换为已有订单/报表服务参数。结构化解析失败时回退现有 DSL，并在运行诊断中记录 `structured_intent_fallback`。

### P4：评测和观测

建立覆盖所有模块的固定语料集：

- 商品：`迪莫商品`、`商品迪莫`、昵称、规格、用途、错别字和多候选。
- 订单：销售/采购混合查询、日期、状态、金额、排序和数量。
- 报表：销售额、实收、应收、采购、现金流等相近口径。
- 草稿：客户、供应商、商品、仓库的同义表达和歧义表达。

每次请求记录脱敏后的：场景、解析方式、工具名、候选数量、最终匹配方式、语义可用性、耗时和稳定错误码；不记录不必要的业务正文或密钥。

验收指标至少包括：

- 精确实体 Top-1 ≥ 99%。
- 常见同义/词序表达 Top-1 ≥ 95%。
- 无权限或不存在实体不得返回事实候选。
- 语义不可用时 lexical fallback 可观测且回答不声称已完成语义检索。
- 订单/报表结构化解析失败不会绕过后端权限和参数白名单。

## 四、当前验证结论

2026-07-26 本地只使用临时进程环境完成对比，没有提交代码或修改 staging：

- 关闭语义时，`商品Camera` 走 `lexical_fallback` 且查不到。
- 开启语义时，`商品Camera` 返回 `SKU010 / Camera`。
- `帮我找适合拍照的相机` 在关闭语义时也能靠昵称/关键词找到 Camera；开启语义后 Camera 仍排第一，但由于本地索引只有 179 个点且包含测试数据，出现了低质量额外候选。
- 本地当前商品总数约 904，已索引约 179，说明“开启开关”不等于“索引质量已经达标”。
- staging 之前对“商品迪莫”做过临时开启语义的真实冒烟，成功返回商品“迪莫”；staging 持久配置仍未修改。

这些结果证明：

1. “查询迪莫”这类精确查询可以直接走普通商品接口，不必依赖向量索引。
2. 语义向量确实能解决词序、同义词和描述性表达，但必须建立高覆盖、低噪声索引。
3. 当前最需要改进的是统一实体解析和结构化意图边界，而不是继续堆叠单个词组正则。

## 五、非目标与安全边界

- 不让模型直接连接 MariaDB、Frappe ORM 或 Qdrant 管理接口。
- 不使用模型输出作为库存、价格、订单状态或权限事实。
- 不因语义相似度高就自动创建商品、订单、库存调整或提交单据。
- 不把“结果查询成功”解释为“业务正常”；业务健康必须有明确字段和独立口径。
- 不在索引缺失时静默伪装成语义检索成功。

## 六、实施顺序

1. 先实现共享商品实体解析和精确/关键词优先级，补齐 `商品迪莫`、`迪莫商品` 等词序用例。
2. 在本地完成全量索引、噪声清理和评测集门禁。
3. staging 通过门禁后持久启用向量检索，并验证普通商品查询、销售/采购/库存草稿共用解析器。
4. 再实现结构化订单/报表意图解析，保留现有 DSL 作为失败兜底。
5. 最后按评测结果决定客户、供应商、仓库是否需要独立语义索引。

## 七、2026-07-26 结构化意图解析实施状态

- 已新增 Orchestrator 内部端点 `POST /internal/v1/intent/parse`，使用 `erp-intent-v3` Prompt 和严格 JSON Schema 返回只读查询意图、置信度、商品/单据实体、报表口径、日期预设或明确起止日期、状态、排序、金额下限和数量；它不查询 ERP，也不能执行写操作。Frappe 在执行边界重新校验日期、金额、公司、DocType 白名单和权限，模型字段永远不能直接变成数据库过滤器。
- Frappe 保留本地快速规则，但只在本地判断为 `general` 且输入包含商品、库存、订单、报表等业务实体时调用结构化意图解析。Orchestrator 超时、不可用或输出非法时回退本地规则，并在 Run `tool_calls` 中记录 `structured_intent_fallback`。
- 已修复“看看库存和售价”的商品场景识别，以及“最近一个月还没完成的销售订单，金额最高前三张”的否定状态、30 天日期范围、排序和数量解析。规则继续作为快速路径和失败回退，不再被视为长期唯一语义理解器。
- 当前结构化意图已经参与 `general / product_search / order_query / report_summary` 路由，并向商品解析器传递受控 `product_query`，向订单 DSL 传递日期、状态、排序和数量，向报表 DSL 传递日期预设。Frappe 只接受白名单枚举、1～20 数量和置信度不低于 `0.6` 的结果；本地解析出的更具体非默认条件不会被模型默认值覆盖。订单/发票实体和报表类型仍由 Frappe 本地白名单解析，后续可在扩展 Schema 与评测后再迁移。
- `conversation-state-v1` 已接入意图解析：当前消息优先，状态只补全指代和省略；每轮仍重新执行权限、公司范围、DocType 和实时数据校验，成功回答后才写回状态，版本冲突只跳过写回并保留审计。
