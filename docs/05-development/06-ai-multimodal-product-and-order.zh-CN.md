# AI 多模态商品与订单工作流设计

## 1. 目标

本文定义 MyApp AI 工作台的图片输入、模型能力治理、商品照片建档/完善和订单照片生成/修改能力。实现继续遵守现有 AI 工作台的草稿、权限、版本、幂等和人工确认边界，不建立绕过正式领域服务的第二套商品或订单逻辑。

首期支持 JPG、PNG 和 WebP 图片。用户可以在同一条消息中提交文字和最多 4 张图片，图片可来自文件选择、平板/电脑摄像头或移动端相机。

## 2. 核心原则

1. **模型用途与输入模态分离**：`fast_chat / reasoning / structured / embedding / rerank` 描述主要用途，`supports_vision` 描述是否经过真实图片请求验证。视觉不是纯文本结构化能力的替代品；照片草稿要求模型同时满足图片输入和结构化输出要求。
2. **能力必须实测**：模型名称、供应商宣传和 LiteLLM `/v1/models` 可见性都不能证明视觉能力。可用性检查必须发送合成图片并验证回答，失败时保持 `supports_vision=false`。
3. **原始证据与业务图片分离**：用户上传图片先保存为私有、短期 AI Attachment。创建新商品且用户没有指定其他图片时，系统可生成暂存商品封面候选；完善现有商品默认保留正式商品图片，只有用户明确要求使用或替换某张会话图片时才生成图片 patch。修改订单不会改变业务图片。
4. **模型负责理解和规划，后端负责事实和写入**：模型可以根据图片和用户目标提取字段、调整搜索词并提出候选；真实商品、客户、供应商、订单、UOM、价格、权限和单据状态由 Frappe 重新解析。
5. **不猜测缺失字段**：图片或文字没有明确证据的规格、单位、数量、价格、币种、仓库、客户、供应商和日期保持为空或待确认。
6. **正式写操作仍需确认**：模型只生成或更新 AI Draft。用户确认当前版本后，Backend 才调用现有商品、销售订单或采购订单领域服务。

## 3. 模型能力治理

模型注册表继续保留单一主要 `capability`，并增加/展示下列正交能力：

- `supports_streaming`
- `supports_tools`
- `supports_json_schema`
- `supports_vision`
- 最近一次文本、工具和视觉探测状态与稳定错误码

模型同步只建立库存记录。批量可用性检查按以下顺序执行：

1. Chat 或 Embedding 最小请求；
2. Chat 模型 Function Calling 探测；
3. Chat 模型红色、蓝色两张合成图片的双挑战；Prompt 不包含预期答案，两张图都必须返回精确的小写英文颜色词。

视觉探测失败不应把一个可用的纯文本模型整体标记为不可用，只将 `supports_vision` 置为 false 并记录 `vision_error_code`。照片请求进入 Runtime Policy 后，只能从当前策略主模型和 fallback 中选择 `supports_vision=true` 的模型；固定模型不支持图片时请求失败关闭，不允许静默丢弃图片。

## 4. AI Attachment

### 4.1 生命周期

```text
浏览器选择/拍照
  → Backend 真实图片校验与 EXIF 修正
  → 私有 AI Attachment（uploaded）
  → 绑定用户消息、会话和 Run（bound）
  → 作为所属用户消息的图片内容块，仅发送给 Orchestrator/LiteLLM
  → 跟随会话保留期；活动草稿引用期间继续受保护
```

AI Attachment 至少记录：owner、Frappe File、SHA-256、MIME、尺寸、字节数、状态、会话、消息、Run、用途和保留截止时间。浏览器只能引用当前用户尚未过期的 Attachment ID，不能提交任意服务器文件 URL。

Backend 会在发送给模型前执行真实图片解码，校验实际格式与声明 MIME 一致，再做 EXIF 方向修正并统一转为 WebP。视觉证据图最长边最多 2400 像素，只允许等比缩小，不对小图做无意义放大；这样既保留原始可见信息，也避免放大后增加图片 Token 预算和传输体积。商品图片继续使用独立的 `item-flexible-v2` 处理规则，不受该“不放大”约束影响。

Orchestrator 使用图片尺寸参与请求预算，按每张 `85 + 170 × ceil(width/512) × ceil(height/512)` 估算输入 Token；缺少尺寸的兼容请求按 1024×1024 估算。base64 正文不进入文本字符估算或默认可观测内容采集。

未绑定消息的上传附件默认保留 24 小时。附件绑定用户消息后，其有效期跟随会话 `retention_until`，会话继续活跃时同步延长；若活动 AI Draft 仍引用附件或由其派生的暂存商品图片，则继续延迟清理。历史上下文按消息恢复附件，不能把所有历史图片重新挂到最后一条用户消息。图片原文、base64 和私有文件地址不得进入普通日志、错误正文或 Langfuse 内容采集。

聊天内核的完整分阶段改进、消息级附件兼容策略和可恢复运行设计见 `07-ai-chat-core-v2.zh-CN.md`。

### 4.2 商品封面派生规则

- `operation=create` 且草稿没有人工指定图片：第一张来源图片生成 `item-flexible-v2` 暂存商品图片，并作为默认封面候选。
- `operation=update`：普通识别或资料完善请求不把来源图片写入草稿 patch，已有商品图片只作为权威 baseline 展示；用户明确说“图片使用我发的图片”“把刚才那张设为主图”等替换意图时，才把被引用 Attachment 派生为暂存商品图并写入 patch。
- 历史图片选择采用受控规则：优先使用模型 `evidence[].attachment_id` 指定且确实属于当前用户、当前会话有效消息窗口的附件；没有精确 evidence 时，只有当前文字明确引用历史图片才回退到最近一条带图消息的第一张图。不得扫描或复制全部会话图片。
- Orchestrator 在每张图片前加入服务端生成的 Attachment ID 标记；商品结构化 Prompt 对图片来源字段保存 evidence，明确主图意图使用 `field=image / value=use_as_product_image`。Backend 仍验证 ID 必须存在于本轮有效上下文，不能信任模型任意生成的 ID。
- 用户在草稿编辑器中后续手工选择替换图片时，继续使用现有 `ItemImageUpload` staged/immediate 语义。
- 图片不符合商品封面比例或质量要求：保留其 AI 证据用途，草稿图片留空并提示用户另选封面。

## 5. 商品照片工作流

模型从图片和文字中提取可见证据，包括商品名称、品牌、条码、可见编码、包装文字、规格描述和明确价格。每个字段可携带来源附件、证据文本和置信度，但置信度不能替代后端匹配。

Backend 按以下优先级搜索当前用户可读商品：

1. 商品编码或条码精确匹配；
2. 商品名称、品牌和规格的精确/包含匹配；
3. 现有权限安全的商品语义检索。

结果分为：

- `unique`：唯一明确商品；
- `ambiguous`：存在疑似相同商品，草稿必须要求用户选择“新增商品”或具体的“完善现有商品”；
- `not_found`：没有可信候选，按创建草稿整理已提取字段。

用户明确要求修改商品时，即使没有唯一候选也不能自动转为创建；用户明确要求新增且存在疑似重复商品时，仍允许选择新增，但必须展示重复提醒。

## 6. 订单照片工作流

销售和采购订单照片共用以下原则：

- 提取订单号、往来单位、日期、商品行、数量、单位、单价、金额和备注；未出现的字段保持为空。
- 商品缩写或非严格名称进入 `item_query`，由 Backend 返回真实商品候选；模型不能直接生成内部商品编码。
- 图片中的价格是用户来源价格候选，只有现有草稿和正式领域服务允许人工价格时才能采用；否则使用后端参考价并保留提示。
- 图片中明确可见的行单价在首次生成草稿时按 `price_source=user` 保存，同时保留后端参考价用于复核；它不能被参考价静默覆盖，也不能绕过人工确认直接进入正式订单。
- 表格合计不能反向推导缺失单价、数量或税率。

若检测到订单号：

1. 先按销售/采购订单命名规则识别是否可能属于本系统；
2. 用户要求修改时，按当前账号权限读取真实订单作为 baseline；
3. 图片值只形成 patch，未在图片或文字中明确出现的字段不覆盖现有订单；
4. 草稿确认执行时复用现有订单更新服务，由其处理已提交单据、取消/修订、下游单据和幂等限制。

修改草稿保存来源订单的 `modified` 版本。用户编辑草稿时，Backend 根据明细真实差异决定是否明确替换明细；执行前再次读取来源订单，版本不一致时要求重新生成草稿。表头更新后，明细替换继续使用最新 `modified` 做第二次乐观并发校验。

外部系统订单号只作为来源参考，不按本系统主键更新订单。

## 7. 动态编排边界

首期不把流程实现为固定 OCR 步骤列表。模型可以根据用户文字和图片内容选择商品建档、销售订单、采购订单或通用解释场景，并可在受控候选结果基础上调整提取和搜索表达。

以下边界保持确定性：

- Attachment owner、公司和 DocType 权限；
- 模型是否具备经过验证的图片输入能力；
- 商品/订单候选查询和权威 baseline；
- UOM、价格、库存和单据状态；
- 创建/修改分支的用户确认；
- 暂存图片绑定、草稿版本、幂等和正式执行。

## 8. API 契约

新增或扩展：

- `upload_ai_image_attachment_v1`
- `discard_ai_attachment_v1`
- `chat_ai_v1(..., attachment_ids[])`
- `stream_ai_message_v1(..., attachment_ids[])`
- `resolve_ai_scenario_v1(..., attachment_ids[])`
- 四类草稿生成端点增加可选 `attachment_ids[]`
- 四类草稿生成端点增加可选 `retry_run_id`；失败重试由 Backend 恢复原消息、场景、公司、会话和附件，不重复插入用户消息
- Orchestrator `ChatRequest.attachments[]`
- 模型治理可用性结果增加 `supports_vision` 与 `vision_error_code`

会话消息返回权限安全的 Attachment 元数据和预览 URL，不返回磁盘路径、base64 或内部文件标识以外的存储信息。

四类草稿在模型调用、候选解析或草稿持久化失败时，Backend 必须先回滚未完成业务写入，再把 Run 标记为失败，并在原会话写入绑定该 Run 的助手失败占位消息。只有存在这个持久占位，Web 才能使用 `retry_run_id` 原位重试；不得只记录失败 Run 而让会话中没有可重试消息。

## 9. Web 交互

- Sender 上方展示待发送图片缩略图，可删除，最多 4 张。
- 上传完成后再允许发送；上传失败不提交消息。
- 固定模型不支持图片时在发送前阻止并解释；自动模式由发布策略选择视觉模型。
- 图片消息在历史会话中恢复缩略图。
- 商品疑似重复时，在草稿卡片中展示候选和匹配原因，并要求明确选择创建或更新。
- 订单识别保留未匹配行和空字段，编辑器直接显示需要补充的字段，不用占位猜测值。

## 10. 验收标准

1. 纯文本模型收到图片请求时失败关闭，图片不会被丢弃后继续文本推理。
2. 视觉探测成功后模型注册表和 Web 管理台明确显示多模态能力。
3. 新商品照片默认产生暂存封面候选；完善现有商品不自动覆盖图片，但用户明确要求使用当前或历史会话图片时必须形成可审计的图片 patch。
4. 疑似重复商品必须经过用户选择，不能自动创建或自动修改。
5. 订单图片缺失规格、单位或价格时对应字段保持空值。
6. 本系统订单号修改路径读取真实订单并受正式更新规则约束。
7. Attachment 不能跨用户、跨公司或过期复用，日志和错误不泄露图片内容。
8. Backend、Orchestrator 和 Web 的目标测试、静态检查与 `diff --check` 通过。
